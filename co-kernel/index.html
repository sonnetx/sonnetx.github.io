Does your kernel still win when the GPU is shared?

Inference stacks pick a kernel by timing it on an empty GPU. The GPU it then runs on is often shared with another tenant, another phase, or another job. co-kernel measures the same candidates alone and next to a neighbor you control, and reports when the ranking flips.

On one H100 at Stanford's Sherlock cluster, it flipped. Two agent-written kernels for the same matrix-vector multiply traded places. Alone, a 512-thread scalar kernel took 66.6 microseconds and a 256-thread vectorized kernel took 82.4, a 24% lead for the scalar kernel. A neighbor holding 127 registers per thread, about half the register file, stretched those times to 143 and 131 microseconds. The kernel you would have shipped was 10% slower.

Kernel Alone Shared Slowdown
512-thread scalar 66.6 µs 143.0 µs 2.15×
256-thread vectorized 82.4 µs 130.5 µs 1.58×

Why the faster kernel lost

The scalar kernel launches 512 threads per block and loads one float at a time. The vectorized kernel launches 256 threads and loads 16 bytes at a time through the read-only path. On an empty GPU the wider launch wins, because a matrix-vector row is limited by how fast it can be read.

An H100 has 65,536 registers per multiprocessor. The neighbor in this run held 127 registers on each of 256 threads, about 32,500 registers, and left about 33,000. A 512-thread block can reside only if each of its threads needs fewer than 64 of those. A 256-thread block can use up to 129. The shorter block still fits. The longer one gets squeezed, and it slows by 2.15× while the other slows by 1.58×.

A ranking flips only when the isolated winner is also the more fragile one, by more than its lead. Here the fragility ratio is 2.15 / 1.58 = 1.36, and the isolated margin is 82.4 / 66.6 = 1.24. Slowing both kernels by the same amount leaves the order alone. That is why a neighbor that makes everything uniformly worse is not the failure mode to worry about, and why picking the two fastest near-duplicate kernels never produced a flip in an earlier run.

Use it on your kernels

The neighbor above is synthetic. It exists to hold one resource still while everything else stays put. The harness does not know what the neighbor is. A corpus is a directory of plain files, and a neighbor is a short interface you implement.

corpus/<slug>/
  kernel.cu    a torch extension exposing forward()
  ref.py       Model, get_inputs, get_init_inputs
  meta.json    level and task_id, so candidates for one problem rank together

Point the sweep at that directory. Each candidate is checked for correctness in the measuring process, timed alone, then timed again at each neighbor level. The result file records the latency summary, the fragility, and whether the isolated winner is still the winner.

pip install torch --index-url https://download.pytorch.org/whl/cu124
pip install -e '.[corpus,clocks]'
./scripts/run_local.sh --quick

To measure against a real neighbor, a decode loop or another tenant, implement CoRunner in cokernel/corunner.py. start returns only once that neighbor is in steady state. stop has to work from another thread, because a starved candidate leaves the main thread blocked inside a CUDA synchronize. The same interface is how you swap the synthetic register sweep for shared memory, or for a workload of your own.

This pair was measured once, on one H100. The register-headroom account fits it, and it does not fit every kernel in the same run: two matmul kernels made no progress even when the leftover registers should have held them. The harness is the way to check a kernel you might actually ship, against a neighbor you might actually have.
