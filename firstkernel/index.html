A faster MoE layer you can install, or replace.

firstkernel is a drop-in for vLLM’s unquantized bf16 SwiGLU path on Hopper, and a harness for whatever you put in its place. The layer is one file and runs in two GPU launches instead of five. On Qwen3-30B-A3B it is 1.216× the tuned kernel at long prefill, and 1.116× once it is back inside the engine.

H100, bf16, vLLM 0.28.x. The bundled launch table is for 128 experts of width 768. Other shapes run, on the heuristic, until you retune them.

Install it

Patch before the engine is built, and keep the worker in-process so the patch reaches it. Quantized paths, LoRA, and expert remapping stay on the stock kernel.

import os
os.environ["VLLM_ENABLE_V1_MULTIPROCESSING"] = "0"
import vllm, firstkernel
firstkernel.install()
llm = vllm.LLM(model="Qwen/Qwen3-30B-A3B")

Or call the layer on tensors shaped the way vLLM already does: moe(hidden_states, w1, w2, topk_weights, topk_ids). Check it on your GPU first with python -m firstkernel.selftest.

Replace it

The kernel is firstkernel/kernel.py. SwiGLU-in-the-epilogue, the atomic top-k reduction, and the TMA weight loads are separate functions, so you can delete one and see what it was worth. Copy the file, expose moe(...), and the harness times it against the tuned reference on identical inputs.

cp firstkernel/kernel.py my_kernel.py
printf 'from my_kernel import moe\n' > kernels/mine.py
python3 harness/bench.py --candidate kernels/mine.py \
    --compare kernels/standalone.py --set dev

A number is reported only if the candidate matches an fp32 implementation of the MoE definition, changes when its inputs change, returns its own buffer, and stays above the HBM-bandwidth floor. src/tune_moe.py rebuilds the launch table for another expert shape or GPU. It ranks candidates, then remeasures the finalists, because a one-stage search picked its own noise at 15 of 15 shapes. Point FK_MOE_CONFIG at your table.

What this one measured

1.216×layer, 16,384 tokens
1.116×vLLM, prefill workload
1.037×layer, 64-token decode
1.020×vLLM, decode workload

Fusion and TMA remove traffic whose share of the layer grows with the token count. Decode is already streaming expert weights at about 75% of peak HBM bandwidth, and that shape is 96% of layer calls in the profiled mix, so the same change has little left to take there.

Stock, five launches
  1. Gate and up GEMM
  2. SwiGLU
  3. Down GEMM
  4. Router-weighted top-k reduction
  5. Write the output
This kernel, two launches
  1. Gate and up GEMM, SwiGLU in the fp32 epilogue
  2. Down GEMM, router weight and top-k sum in relaxed bf16 atomics

At 1,024 tokens and above, both kernels load expert weights through Hopper TMA. The atomic sum is not bitwise deterministic. Repeated runs differed by a few bf16 ulps, about 700× under the tolerance, and greedy decode still matched stock token for token over 2,048 steps. Leave it off where batch-invariant mode matters.

Inside vLLM

Fixed batches, three H100 allocations, three timed rounds each, CUDA graphs on. This is the model and the in-process scheduler. It is not an HTTP server, a queue, or a tail-latency result. About half the relative layer gain was still there: 1.216× became 1.116×, and 1.037× became 1.020×.

Why the bench refuses a number

Each of these looked like a larger win than the kernel. The harness exists so the next person does not have to rediscover them.

16 tokens measured 0.630 ms. The same config later measured 0.280 ms.

Thirty-two tokens went from 0.719 ms to 0.325 ms. The interquartile range at 32 tokens was 0.306 ms against a 0.719 ms median. Another job was on the node, and Sherlock will not lock the clocks for an unprivileged user. Timing now spans three fixed routing draws and is marked unstable when the repetitions disagree.

A one-stage search overstated itself at 15 of 15 shapes.

The tuner kept the fastest of a noisy set of trials. The search that ships ranks candidates, then remeasures the finalists before choosing. The table that survived was 1.015×, and every kernel after that was compared with it.

An unchanged copy of vLLM looked 1.13× faster.

The gap was about 52 microseconds at every token count from 1 to 16,384. That is deleted dispatch, not faster math. Kernel numbers are paired inside the same scaffold. A claim about vLLM is made only after the kernel is installed back into it.
