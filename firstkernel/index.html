The kernel got 22% faster. vLLM got 12%.

Coding agents rewrote the mixture-of-experts layer that dominates Qwen3-30B-A3B on one H100. It runs in two GPU launches instead of five. At long prefill the layer was 1.216× the tuned kernel. Inside vLLM, the same change was 1.116×.

Qwen3-30B-A3B, bf16, one H100 80GB, vLLM 0.28.0. Held-out shapes. Nothing was tuned after the final run.

1.216×layer, 16,384 tokens
1.116×vLLM, prefill workload
1.037×layer, 64-token decode
1.020×vLLM, decode workload

The curve is the mechanism. Fusion and TMA remove traffic whose share of the layer grows with the number of tokens. Decode is already streaming expert weights at about 75% of peak HBM bandwidth, so the same change has little left to take. Ninety-six percent of layer calls in the profiled serving mix were the 64-token shape.

Two launches

Stock, five launches
  1. Gate and up GEMM
  2. SwiGLU
  3. Down GEMM
  4. Router-weighted top-k reduction
  5. Write the output
This kernel, two launches
  1. Gate and up GEMM, SwiGLU in the fp32 epilogue
  2. Down GEMM, router weight and top-k sum in relaxed bf16 atomics

At 1,024 tokens and above, both kernels load expert weights through Hopper TMA. Four agents each got one strategy and ten benchmark submissions. A fifth composed the three that were compatible. The fourth, on small decode shapes, mostly found that the tuned kernel was already hard to beat.

The atomic sum is not bitwise deterministic. Across repeated runs the spread was a few bf16 ulps, about 700× under the correctness tolerance. Greedy decode still matched stock token for token over 2,048 steps.

Checks that removed more than the kernel added

Before the final numbers, the same pipeline produced larger speedups that were wrong. Fixing the measurement threw out more than the optimization eventually found.

16 tokens measured 0.630 ms. The same config later measured 0.280 ms.

Thirty-two tokens went from 0.719 ms to 0.325 ms. The first writeup blamed vLLM’s untuned launch config. The interquartile range at 32 tokens was 0.306 ms against a 0.719 ms median: the repetitions disagreed by more than 40%. Another job was on the shared node, and Sherlock does not let an unprivileged user lock the GPU clocks. Routing luck moves a timing by up to 1.16×, which is already larger than most of the gains here, and it still does not explain that cliff.

A one-stage search overstated itself at 15 of 15 shapes.

The config tuner kept the fastest of a noisy set of trials, so it preferred lucky samples. One apparent winner was slower when the same configs were measured again. The search that shipped ranks candidates cheaply, then remeasures the finalists before choosing. The table that survived, for 128 experts of width 768, was a 1.015× improvement, and every kernel after that was compared with it. Beating the untuned heuristic would have proved nothing.

An unchanged copy of vLLM looked 1.13× faster.

The gap was about 52 microseconds at every token count from 1 to 16,384. That is deleted dispatch and workspace overhead, not faster math. CUDA graphs amortize much of it once the kernel is back in the engine. Kernel numbers in this project are paired against that same scaffold. Claims about vLLM are made only after the kernel is installed back into it.

What reached the engine

Fixed batches, three H100 allocations, three timed rounds each, CUDA graphs on. This includes the model and the in-process scheduler. It does not include an HTTP server, a queue, or per-request tail latency.

Every workload, allocation, and round improved. Prefill batch latency went from 1.117 s to 1.001 s. Decode step time went from 14.07 ms to 13.80 ms. Relative to the layer, about half the gain was left: 1.037× became 1.020×, and 1.216× became 1.116×.

Decode sits on a 2% bar written down before the run. Pooling every round gives 1.96%. The median across allocations gives 2.45%, and the worst allocation was 1.92%, with all nine comparisons positive. Both readings are real. The summary is about 2%.

Use it

Hopper only, bf16, unquantized SwiGLU. Quantized paths, LoRA, and expert remapping stay on the stock kernel. The bundled launch table is for E=128, N=768. Output is tolerance-correct and not bitwise reproducible, so leave it off where vLLM’s batch-invariant mode matters.

import os
os.environ["VLLM_ENABLE_V1_MULTIPROCESSING"] = "0"
import vllm, firstkernel
firstkernel.install()
llm = vllm.LLM(model="Qwen/Qwen3-30B-A3B")
